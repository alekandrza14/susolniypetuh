MYENGINE R24.1 — ЖУРНАЛ ВХОДОВ И СЕРТИФИКАТ ВЛАДЕЛЬЦА

ОБНОВИТЬ УЖЕ РАБОТАЮЩИЙ СЕРВЕР
1. Замени файлы существующего репозитория сервера файлами из
   MyEngine_PlayerIdentity_Server_R24.zip и обнови существующий сервис Render.
2. Сохрани DATABASE_URL, OWNER_*, PUBLIC_BASE_URL, настройки SMS и телефона.
   Новая база, новые API-ключи и повторный запуск setup_owner.cmd не нужны.
   Таблицы добавляются автоматически, имеющиеся регистрации сохраняются.
3. Открой https://АДРЕС-СЕРВЕРА/moderation и войди своим номером и паролем.
   Ниже заявок появятся «Журнал безопасности» и «Сертификат разработчика».
4. В игру / редактор установи MyEngine_Update_R24.zip. Он обновляет передачу
   заявленного типа сертификата и шаблон экспортируемого сервера.

ЖУРНАЛ БЕЗОПАСНОСТИ
Виден только после входа владельца в кабинет. Обычный игрок его читать не может.
Показывает:
— успешные и отклонённые входы в кабинет и подтверждения входа в игру;
— запросы входа из игры, новые заявки, решения автора;
— время, ID игрока, подтверждённую роль (владелец / игрок / не подтверждена);
— IP, источник IP, адрес соединения сервера с прокси;
— браузер, ОС и название устройства, указанное человеком;
— сертификат и товар, изменение привязки сертификата владельца.

Отмечаются смена IP, случайного идентификатора браузера и браузера / версии
относительно последнего успешного входа этого аккаунта в соответствующий раздел.
Неудачный вход не становится эталоном для следующих сравнений.
Есть кнопка завершения остальных сеансов кабинета; текущий сеанс сохраняется.
Она не меняет пароль и не завершает игровые сеансы. Для компрометации пароля
нужно также заменить OWNER_PASSWORD_HASH своим привычным способом.

Журнал начинается с обновления R24: прошлые входы восстановить нельзя.
Хранится до 30 дней и максимум 10 000 событий. Старые записи удаляются при новых
событиях; API скрывает записи старше 30 дней даже до очередного удаления.
На странице показывается 100 записей, дальше — кнопка «Ещё события».
Ошибку записи журнала кабинет показывает отдельно; она не выдаёт дополнительных
прав и не отменяет проверку сертификата. Секреты, пароли и SMS-коды в журнал
не записываются. Исходные токены сеансов и идентификаторы браузера не выводятся.

ОГРАНИЧЕНИЯ ДАННЫХ ОБ УСТРОЙСТВЕ
Браузер не предоставляет сайту надёжное системное имя компьютера.
Поле «Название устройства» человек заполняет сам; автоматически hostname
компьютера и имя пользователя Windows не собираются. Поле необязательное.
В localStorage сохраняются это название и случайный ID браузера данного сайта.
Аппаратный fingerprint не снимается. Очистка данных сайта или приватная вкладка
могут выглядеть как новый браузер. Название и User-Agent можно подменить.
Информация о сборе показывается перед входом и регистрацией.

Render передаёт клиентский IP через заголовки прокси. В этой версии первый
корректный адрес X-Forwarded-For показывается как «IP из заголовка прокси —
не подтверждён». Отдельно сохраняется REMOTE_ADDR. Заголовок не используется
как доказательство личности, для автоматического бана или обхода лимитов.
Если заголовка нет / он некорректен, показывается адрес самого соединения.
Смена IP, VPN, мобильная сеть или обновление браузера сами по себе не нарушение.
Страна, политические взгляды и паспортные данные не определяются и не собираются.

ЕДИНСТВЕННЫЙ СЕРТИФИКАТ РАЗРАБОТЧИКА
Сервер содержит одну активную привязку: playerId владельца + productId + certificateId.
Первый успешный вход владельца с паролем закрепляет эту комбинацию.
Если при обновлении уже есть действующий подтверждённый сеанс владельца,
его авторизованный опрос тоже может закрепить прежний сертификат.
Неудачная попытка пароля и истёкший сеанс ничего не закрепляют.
При одновременных попытках с разными сертификатами закрепиться может только один.
После закрепления другой ID / товар у владельца отклоняется сервером.

В кабинете можно явно закрепить или заменить сертификат из уже зарегистрированных
на владельца. Для этого нужно ещё раз ввести пароль владельца. При замене игровые
сеансы владельца со старым сертификатом завершаются. Другие записи сертификатов
в БД не стираются, но больше не подходят для входа владельца, пока выбрана новая.
Кабинет доступен по прежнему паролю отдельно от игрового сертификата, поэтому
исправить ошибочную привязку можно, даже если вход из игры отклоняется.

Для обычных игроков используй grantType=manual или purchase. Если раньше им
выдавались файлы с developer, понадобится обычный сертификат: в R24 developer
зарезервирован для владельца.
Обычная публичная регистрация отклоняет grantType=developer. Подмена поля в JSON
не делает игрока владельцем: роль определяется серверной записью и отдельной
проверкой пароля владельца. В журнале заявленный тип и подтверждённая роль
разделены. Старые клиенты без поля grantType могут войти только по ранее
разрешённой записи и обычной проверке телефона / пароля; новых прав это не даёт.

Сам JSON-файл можно скопировать. «Единственный» здесь означает одну действующую
серверную привязку, а не физически некопируемый файл. Криптографическая подпись
не добавлена: текущий формат сертификатов остаётся неподписанным. Защита опирается
на серверный реестр и подтверждение владельца. В игре должна быть включена
identityRequired / обязательная проверка игрока; локальный режим без сервера
не предоставляет этой защиты, и клиентский код сам по себе не является защитой
от владельца изменённой копии игры.

ОПЛАТА И ВОЗМОЖНАЯ ПОДДЕЛКА
Неподписанное payment.status в файле — заявление клиента, не подтверждение банка.
В заявке показано «Оплата сервером не подтверждена». Поле paid в чужом JSON
не меняет этот статус. Игрок может сообщить, что способ оплаты недоступен;
это показано отдельно как сообщение игрока, без обвинения в подделке.
Никакой проверки страны или доступности ЮMoney по стране здесь нет.

При одобрении автор выбирает:
— разрешить доступ без проверки оплаты;
— выдать бесплатный доступ;
— лично проверил покупку (требуется номер проверенной операции).
Последний вариант сохраняет решение автора и номер в журнале, но не называется
автоматическим подтверждением платёжного провайдера. Автоматическое подтверждение
ЮMoney требует отдельной серверной интеграции, которой это обновление не добавляет.
Ни отправка письма #verify, ни смена IP, ни отсутствие способа оплаты не выдаёт
и не отзывает доступ автоматически. Решение принимает автор по конкретной заявке.

ПРАВОВЫЕ СПРАВКИ R24.1
В карточке отклонённого события появляется раскрываемая строка
«Правовая справка: ст. 272 и 159.6 УК РФ», если:
— запрос входа не совпал с закреплённым сертификатом владельца;
— запрос входа с заявленным типом developer не допущен сервером;
— публичная заявка на регистрацию с типом developer отклонена.
Строка поясняет наблюдаемую причину и допускает ошибку / старый файл.
Она не подтверждает подделку, личность отправителя или состав преступления.
Справка видна в кабинете модератора; игроку она не отправляется.

Статья 272 требует неправомерного доступа к охраняемой законом компьютерной
информации и предусмотренных статьёй последствий. Статья 159.6 требует хищения
чужого имущества или приобретения права на чужое имущество указанным в ней
способом. В кабинете приведены краткие условия и ссылки на полный текст.
Это общая справка, а не юридическое заключение по конкретному событию.
Применимость статьи нужно оценивать по обстоятельствам с юристом.

Успешный вход, смена IP / браузера / устройства, первый вход, неправильный пароль,
недоступность оплаты, отсутствие подтверждения оплаты или обычный отказ
незарегистрированному сертификату сами по себе не вызывают справку.
Автоматических обвинений, банов, сообщений игроку или заявлений в органы нет.
Справки не меняют серверные права, платежи, журнал или существующую базу.
